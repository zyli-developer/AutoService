**飞书 Discuss 任务目标**

在飞书中搭建 `discuss` 命令的核心目标是**让管理群内的所有人能够通过输入命令的形式，基于特定的文件、Git 库或方案进行高效的异步讨论**。因为目前的开发节奏非常紧凑，传统的长会议效率较低，所以需要借助 AI 和 `discuss` 技能包（skill）来辅助团队针对产品需求文档（PRD）、部署方案（deployment）或开发计划进行在线评估和讨论。最终期望通过讨论得出一份包含各项问题看法的核对表（checklist）或矩阵报告，并将其反馈到飞书中作为讨论结论。

**Discuss 任务的方法论与工作流**

1. **以 Skill（技能包）为载体：** 讨论前会先制作一个 `discussion guide`（讨论指南）的 skill，其中定义了讨论的内容、主题以及预设的方案（如执行脚本等）。团队成员加载该 skill 后，系统会按预设准则引导讨论，并在会话结束后生成评估报告。
2. **基于 Git Worktree 的状态管理：** 讨论的目标不依赖本地文件，而是**直接挂载到 Git 仓库上**。后台的 CC（Channel Controller）会维护一个常驻的 worktree，每次开启新会话且超过一定时间时，系统会自动检查并 Rebase 到最新的 `main` 分支。
3. **讨论结果的文件化落盘：** 在讨论过程中产生的建议或缺陷，会被写入到这个 worktree 的特定目录中（如可追踪的 `.rdefect` 文件或目录）。如果讨论发现 Bug，可以自动化转化为 Issue 指派给开发人员，而不是直接在主库上修改代码。
4. **子命令分类拓展（Meta Command）：** `discussion` 被定位为一个基础的元命令（Meta Command），它可以包含多类子命令以应对不同的讨论场景。例如：
   * `explain`：用于向大家解释新的方案。
   * `feature request`：用于提出和记录新的功能需求。
   * `debug`：用于处理调试相关的问题。

**在飞书中搭建 Discuss 命令的有用信息与执行细节**

为了在飞书中成功上线此功能，你需要关注以下具体的部署和配置步骤：

* **环境与前置准备：** 需要使用管理员账号登录并查看当前正在运行 `auto service` 的 Tmax session 代码结构。
* **创建新路由与节点：** 需要启动一个新的 CC 路由节点，专门用于处理 `discussion` 指令。
* **使用 Creator 创建指令：** 飞书中的 `discussion` 命令需要通过内置的 `meta command creator`（技能生成器）来创建。这个 Creator 在创建指令的同时，会**启动一个新的 CC 进程去负责路由（root），并且会重启相关的 channel Server 将配置传导过去**，而不是在主库中操作。
* **命令与 Worktree 的对应关系：** 在架构上，飞书中的一个特殊 command（如 discussion）会对应后台的一个独立 worktree（如 auto service worktree），后台文件会告诉系统针对这个 skill 新开一个工作区。
