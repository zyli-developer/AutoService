# IM 软件需求清单 · 飞书能力对照评估

> 配套：`AutoService-PRD.md` v1.0 / `AutoService-UserStories.md` / `autoservice-full-journey.html`
> 版本：v0.1 · 2026-04-14 · 作者初稿
> 目的：梳理 AutoService 对 IM 底座的全部能力要求，对照飞书（Feishu）官方开放平台能力，从 **功能完备性 / 接入便捷性 / 运维便利性** 三个维度给出评估结论，作为选型与实施的参考。

---

## 0. 范围说明

- **对照对象**：飞书（Feishu，中国大陆版）/ Lark（海外版）—— 本文主要指飞书，Lark 差异在"地区与海外部署"小节单独说明。
- **不在本次范围**：WhatsApp / Slack / 微信 / Discord 等其他 IM（如需扩展再开一份对照）。
- **资料口径**：本次评估基于开放平台公开能力（截至 2025-Q2 作者知识时点），具体 API 行为和限额请以官方最新文档为准；文中标注 ⚠ 待核实 的条目请在实施前复核。
- **C 端触点的边界**：飞书是 to-B 协作平台，**不直接服务独立站的 C 端客户**。AutoService 面向 C 端的"独立站浮动聊天按钮 / PSTN 电话呼入 / 20+ 语种客户渠道"需要自建或对接其它通道，**飞书仅覆盖商户侧（管理群 + 客服分队频道）**。本文把 IM 需求也拆分成"商户侧"和"C 端"两类。

## 2. 飞书能力三维评估

### 2.1 维度一：功能完备性

> 飞书提供 / 部分提供 / 不提供，以及是否可自建封装。

| 需求 | 飞书原生能力 | 评级 | 说明 |
|---|---|---|---|
| R-CHAT-1 建群+Bot入群 | `im/v1/chats` create API；Bot 通过 App 授权入群 | ✅ 完备 | 标准能力 |
| R-CHAT-2 Agent 分队频道 | 通过多次建群 + Bot 身份区分实现 | ✅ 完备 | 无"分队"一等公民概念，但建模简单（1 频道 = 1 分队） |
| R-CHAT-3 一键权限 | 开放平台权限清单是"应用级"授权，非"群级勾选"；一键勾选需 App 端自己封装 UI | ⚠ 部分 | 底层 API 齐全，但"一键勾选 4 项"是 AutoService 产品 UX，需自己把开放平台权限申请流程封装掉 |
| R-CHAT-4 成员变更事件 | `im.chat.member.user.added_v1` / `deleted_v1` | ✅ 完备 | |
| R-MSG-1 文本多语言 | `im/v1/messages` 支持任意 UTF-8 | ✅ 完备 | |
| R-MSG-2 互动卡片 | 飞书 Card / Card 2.0（含 button / select / input 组件） | ✅ 完备 | 组件丰富 |
| R-MSG-3 **流式刷新卡片** | Card 2.0 支持流式更新 / `patch_card` 接口可更新已发送卡片 | ✅ 完备 | ⚠ 实际刷新频率限额需核实；经验值单卡片 ~10 次/秒级别 |
| R-MSG-4 **占位+续写替换** | `PATCH /im/v1/messages/:message_id` 可更新消息内容 | ⚠ 部分 | 飞书支持更新消息，但客户端是否"无缝替换"体验（无闪烁/抖动/重新通知）需要实测；Card 流式比普通文本更新更适合这个场景 |
| R-MSG-5 @mention | `text` / `card` 消息均支持 @ 语法 | ✅ 完备 | |
| R-MSG-6 未读徽章 | 频道级未读由客户端原生维护 | ✅ 完备 | 无需开发 |
| R-MSG-7 附件上传 | `im/v1/files` / `im/v1/images` | ✅ 完备 | 文件大小与类型限额需核对 ⚠ |
| R-MSG-8 Markdown / 富文本 | 卡片 + `post` 富文本消息类型 | ✅ 完备 | |
| R-CMD-1 斜杠命令 | 飞书支持「自定义机器人指令」+ 消息解析 | ✅ 完备 | 注意：飞书的「指令」菜单化注册体验优于自己解析文本 |
| R-CMD-2 卡片按钮回调 | `im.message.interaction.click_v1` / Card Action | ✅ 完备 | |
| R-CMD-3 对话监管窗（Copilot UI） | 飞书**没有**原生"侧栏副驾驶"形态；需要自建 Web 应用/网页侧边栏嵌入 | ❌ 不提供 | 可通过「机器人跳转应用」或 Web App 嵌入；客户端不感知的"监管模式"必须 AutoService 自行实现 UI 协议 |
| R-CMD-4 侧栏副驾驶 | 同上 | ❌ 不提供 | 需自建 |
| R-EVT-1..5 事件订阅 | 事件订阅平台完备，100+ 事件 | ✅ 完备 | |
| R-OPS-1 SLA 告警推送 | 用建群 API 找到租户管理群 + 消息发送 | ✅ 完备 | 纯应用层 |
| R-OPS-2 审计日志 | 应用行为可自己落库；飞书自身提供开放平台操作审计（管理员维度） | ⚠ 部分 | AutoService 业务审计需自己实现；飞书审计只覆盖应用配置变更 |
| R-OPS-3 多租户隔离 | 飞书商店应用：每企业独立授权；自建应用：单租户 | ✅ 完备 | 选商店应用模式 |
| R-EXT-1 独立站浮动按钮 | 飞书不提供面向 C 端独立站的 Web Chat SDK | ❌ 不提供 | AutoService `web/` 已实现 |
| R-EXT-2 PSTN 呼入 | 飞书无 PSTN 网关 | ❌ 不提供 | 需第三方 |

**小结（功能完备性）：**
- 商户侧 IM 能力（R-CHAT / R-MSG / R-EVT / R-CMD1-2 / R-OPS）**基本完备**，仅少数项需 App 端自己封装 UX。
- **致命短板** 是 R-CMD-3/4 的"对话监管窗 / 副驾驶侧栏"——飞书没有原生形态，需要 AutoService 自建 Web 侧边栏应用。
- **范围外**：R-EXT-1/2/3（C 端通道）本就不是 IM 底座职责，飞书在此不减分。

- 速率限制是**需要实测**的潜在风险（尤其 R-MSG-3 流式卡片 + 高并发对话）。

| Epic | 关键 IM 能力需求 | 飞书满足度 | 主要 Gap |

| E3 双账本/仪表盘 | 斜杠命令 / 告警推送 / 卡片仪表盘 | 🟢 90% | 仪表盘可以用卡片做轻量版，完整版仍建议 Web 后台 |

**总体评估：飞书作为"商户侧 IM 底座"匹配度约 80%+**，核心短板集中在两处：
1. **监管窗 / 副驾驶侧栏**（R-CMD-3/4）需要 AutoService 自建 Web 应用嵌入飞书
2. **地区割裂**（飞书 vs Lark）对跨境商户是结构性限制

## 4. 关键 Gap 与缓解建议

### Gap 1 · 监管窗与副驾驶侧栏（R-CMD-3/4）

**问题**：飞书无原生"点开卡片弹出对话监管窗 + 侧栏副驾驶"形态。
**缓解**：
- 采用**飞书网页应用**（H5）嵌入，通过 `url` 类卡片按钮跳转到 AutoService 自建的监管窗 Web UI
- 在 H5 内消费飞书 JS-SDK，读写当前飞书会话身份，实现"客户端不感知"的只读镜像
- 监管窗内的"Agent driver / 人工 driver"角色切换由 AutoService 后端状态机管理，飞书只作通知载体

### Gap 2 · 流式卡片刷新频率（R-MSG-3）

**问题**：Card 2.0 流式更新有速率限额，高并发 Agent 分队场景是否撑得住未验证。
**缓解**：
- 按"卡片 = 单对话摘要"为颗粒度，摘要以"N 秒聚合"而非"每消息刷新"
- 使用 patch_card 的 diff 更新而非全量重绘
- 建立**运维压测脚本**（建议在 `e2e/` 下新增 `feishu_streaming_stress.py`），确定单应用 QPS 承载上限

### Gap 3 · 占位+续写的客户感知（R-MSG-4）

**问题**：`PATCH messages` 在飞书客户端的视觉表现（是否无缝替换、是否二次弹通知）需实测。
**缓解**：
- 倾向用**流式卡片**承载"稍等 → 结果"场景，而非普通文本消息的二次编辑
- 如果必须用文本消息，1s 占位 + 15s 续写之间要尽量避免跨屏/跨输入框切换带来的闪烁

### Gap 4 · 权限审批阻塞 ≤2h 自助上线（R-CHAT-3）

**问题**：部分敏感权限需飞书工单审批，审批周期不可控。
**缓解**：
- AutoService 作为**商店应用**预先完成高风险权限的平台级审批，租户侧授权走"应用商店一键安装"流程（通常秒级）
- 梳理一份"基础权限清单"（上线最小集）和"增强权限清单"（用户按需再申请），确保最小集开箱可用

### Gap 5 · 地区割裂（飞书中国 vs Lark 海外）

**问题**：目标客群如果是"跨境商户"，单一端无法覆盖。
**缓解**：
- 短期：明确首发客群为单一地区（如优先国内），接入时只维护飞书一套
- 中期：抽象出 `autoservice/channel/im/` 层，飞书和 Lark 共用 90% 代码，仅 host/auth 差异化
- 长期：同一商户需要双端时，在工作区账号层做身份映射（AutoService 内部用户 ID → Feishu user + Lark user 双绑定）

### Gap 6 · SDK 生态之外（MCP）

**问题**：飞书无 MCP 支持，AutoService 的 MCP 工具桥接完全在 `feishu/channel.py` 本地实现。
**缓解**：维持现状；未来如果飞书推出 MCP/Agent Gateway 再评估迁移。

## 5. 结论与建议

1. **选型结论**：飞书作为 AutoService **商户侧** IM 底座 —— **推荐采纳**，整体匹配度 80%+，短板均可通过应用层封装或自建 Web 侧边栏缓解，无结构性阻塞。
2. **不适用范围**：C 端独立站 / PSTN / 20+ 语种 C 端体验，**不要期待飞书覆盖**，继续由 `web/` + 外部通道承担。
3. **实施优先顺序**：
   1. 监管窗 Web H5 原型（Gap 1）—— 这是 Epic 2 能否落地的关键决定项
   2. 流式卡片压测（Gap 2）—— 承诺 CSAT/首响前需要
   3. 权限清单分层（Gap 4）—— 承诺 ≤2h 自助上线前需要
   4. 审计层自建（Gap R-OPS-2）—— 可与 Dream Engine 同期推进
4. **未决 / ⚠ 待核实项（合并）**：
   - R-MSG-3 流式卡片单卡/单应用刷新速率限额
   - R-MSG-4 `PATCH messages` 在客户端的视觉连续性
   - R-MSG-7 附件大小与类型限额
   - R-OPS-1 消息 API 速率限额的全量矩阵
   - Lark 海外版本与飞书的能力 / 限额差异
5. **横向对比扩展**：当前只评估飞书；如果需要对比 WhatsApp Business Platform / Slack / 微信客服 / Discord，建议再开一份同结构文档。
