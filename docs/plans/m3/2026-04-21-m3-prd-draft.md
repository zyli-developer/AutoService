## 0. 背景与 M2 交接

### 0.1 M2 已落地能力（作为 M3 前提）

- Tenant sandbox fork runtime（plugins/<tid>/souls 全链路）
- 5 agent role 完整（customer / lead / translate / triage / dream）
- Dream agent + DreamScheduler 后台自动运行
- `_master` + `_local_admin` 内置租户
- Magic-link 最小鉴权（admin-portal 两端）
- **Triage 分流 dispatch**（本次新增：customer → 按意图路由到 customer/lead/translate）

### 0.2 M3 要解决的核心问题

| 痛点 | 现状 | 影响 |
|------|------|------|
| **无 operator 鉴权** | operator WS 无登录、无 RBAC | **任何生产部署都不能开门**；连 intranet 也不敢 |
| **无 subtenant 能力** | B 的 tenant 里不能再开 C | B 做 whitelabel / 代理模式的商业路径堵死 |
| **Triage 增强断档** | 今天只做最小 fallback，SLA 监控粗糙；agent 不能主动 handoff | 对大客户场景精细度不足；triage 稳定性对 M2 只是 MVP |
| **合规 country filter 缺失** | PRD gap A-④ 未做 | 跨国租户接入困难 |
| **运营工具链缺位** | 沙盒 GC / 多管理员 / E2E 自动化都无 | 内测阶段可以忍，规模上不来 |

### 0.3 M3 设计原则

1. **Production-readiness over new features**：M3 核心目标是"让 M2 MVP 能开门做生意"——优先做 gating 上线的必备项（鉴权、合规 filter），其次做业务扩展（subtenant）
2. **Triage 收尾**：M2 的 triage 是 MVP 落地，M3 补齐 handoff 协议 + SLA 精细监控（承诺项兑现）
3. **不扩 dream 的自动程度**：dream proposal 自动落地的红线不动；M3 只做"半自动 apply"（低风险 + 人 A review + 人触发）
4. **推后"锦上添花"项**：OAuth、自定义域、跨租户学习、translate wrapper — 都推到 M4+

## 1. Epic 清单（按主题）

### Epic E1 · 身份与权限（Identity & RBAC）

**目标**：operator / client / admin 多层身份系统上线，支持 per-tenant 团队管理。

| Story | 描述 | 来源 | 建议 P |
|-------|------|------|--------|
| E1.1 | Operator 鉴权：登录 + session + 强制 WS 握手校验 | M2 §0.2 | **P0** |
| E1.2 | Per-tenant operator 列表 + CRUD | M2 §0.2 | **P0** |
| E1.3 | Operator 团队邀请链接（magic-link 复用） | M2 §0.2 | **P0** |
| E1.4 | RBAC：operator 分 3 级（viewer / responder / admin）+ 权限矩阵 | M2 §0.2 | **P1** |
| E1.5 | 多管理员登录（1 个 tenant 可有多个 tenant_admin） | M2 §0.2 | **P1** |
| E1.6 | Admin 邀请 admin 链接 | M2 §0.2 | **P2** |
| E1.7 | OAuth / SSO / 2FA / passkey | M2 §0.2 | **P3（推 M4+）** |

**关键技术决策**（待 A 拍板）：
- Session 存储：仍用 `.autoservice/database/sessions.db` 还是加 Redis？
- RBAC 粒度：先做"role-based"还是"permission-based"？
- Operator session 和现有 magic-link cookie 的边界

### Epic E2 · Subtenant 多层架构（Tier 2 实装）

**目标**：B 的 tenant 可以再开 C（whitelabel / 代理模式）。

| Story | 描述 | 来源 | 建议 P |
|-------|------|------|--------|
| E2.1 | B 的 admin-portal 加 "Enable subtenant" 开关 | M2 §10 | **P1** |
| E2.2 | 开关打开 → B 升级为 ControlLayout（仿 master） | M2 §10 | **P1** |
| E2.3 | B 跑 subtenant 创建 wizard（ingest → soul gen → publish） | M2 §10 | **P1** |
| E2.4 | `/publish` 走"fork 内 emplace"把 C 物料落到 `plugins/C/` | M2 §10 | **P1** |
| E2.5 | C 租户的计费归到 B 账上（按 tier_2 费率） | 新 gap | **P2** |
| E2.6 | C 租户的合规独立于 B 配置 | 新 gap | **P2** |

**关键技术决策**：
- Subtenant URL 前缀约定（`/t/<b_id>/t/<c_id>/` 还是 `/s/<c_id>/`？）
- B 是否可以看 C 的对话（B 有 operator 权限下到 C 吗）
- 三层计费模型（tier_0 平台、tier_1 B、tier_2 C）

### Epic E3 · Triage Dispatch 增强（M2 承诺收尾）

## 2. 优先级矩阵

### P0 · 必须进 M3（否则 M3 不能称为可上线 milestone）

- E1.1 Operator 鉴权
- E1.2 Per-tenant operator CRUD
- E1.3 Operator 邀请链接

**理由**：没这三项任何生产部署都没法开门。M3 的 "可上线" 定义 = 这三项完成 + M2 所有能力保持。

### P1 · 强烈建议（M3 gate 尝试包含）

- E1.4 / E1.5 RBAC + 多管理员
- E2.1-E2.4 Subtenant 核心链路
- E3.1 / E3.2 Triage Handoff + SLA 监控
- E4.1 合规 country filter

**理由**：P0 是开门必需，P1 是"内测开始带规模的必须"。如 M3 工期吃紧，E2（subtenant）可拆到 M3.5 迷你冲刺，但不能晚于 M4。

### P2 · 择机（有余量就做，没余量推 M4）

- E1.6 Admin 邀请 admin
- E2.5 / E2.6 Subtenant 计费 + 合规
- E3.3 / E3.4 Triage 配置 DB 化 + 历史压缩
- E4.2 新国家合规集
- E5.1 / E5.2 Platform dream + proposal 半自动
- E6.1 / E6.2 沙盒 GC + Playwright E2E

### P3 · 推 M4+

- E1.7 OAuth / SSO / 2FA / passkey
- E3.5 / E3.6 Translate wrapper + Summary seeding
- E4.3 合规热更新
- E5.3 Dream 跨租户学习
- E6.3 自定义域 + DNS

## 3. 依赖与排序

### 3.1 内部依赖

```
E1.1 Operator 鉴权 (P0)
  ├── E1.2 Operator CRUD (P0)      ── 依赖 E1.1
  ├── E1.3 邀请链接 (P0)            ── 依赖 E1.1
  ├── E1.4 RBAC (P1)                ── 依赖 E1.1 + E1.2
  └── E1.5 多管理员 (P1)            ── 依赖 E1.1

E2.1 Subtenant 开关 (P1)
  └── E2.2 ControlLayout 升级 (P1) ── 依赖 E2.1 + E1.4 (需要 RBAC)
        └── E2.3 创建 wizard (P1)   ── 依赖 E2.2
              └── E2.4 Publish (P1) ── 依赖 E2.3

E3.1 Handoff 协议 (P1)              ── 依赖 M2 triage dispatch 完成
E3.2 SLA 监控 (P1)                  ── 依赖 M2 cc_pool 懒子池

E4.1 Country filter (P1)            ── 独立
E5.1 / E5.2 Dream 扩展 (P2)         ── 依赖 M2 dream pool 稳定
```

### 3.2 建议批次

| 批次 | 内容 | 预估时长 |
|------|------|---------|
| **B-M3-0** | 契约冻结（Auth protocol + RBAC schema + Subtenant tier_2 schema） | 1 天 |
| **B-M3-1** | E1.1-E1.3 Operator 鉴权 + CRUD + 邀请（P0） | 2 天 |
| **B-M3-2** | E1.4-E1.5 RBAC + 多管理员（P1） | 1.5 天 |
| **B-M3-3** | E2.1-E2.4 Subtenant 核心链路（P1） | 3 天 |
| **B-M3-4** | E3.1 Handoff + E3.2 SLA 监控（P1） | 2 天 |
| **B-M3-5** | E4.1 Country filter（P1） | 1 天 |
| **B-M3-6 (可选)** | E1.6 + E2.5/6 + E3.3 + E5.1/2 + E6.1/2（P2 按余量） | 2-4 天 |
| **M3 gate** | smoke test + merge + tag v1.2.0-mvp | 0.5 天 |

**估算**：P0+P1 约 **10.5 天**；带 P2 约 **14-16 天**。实际 M3 执行预算由 A 定。

## 5. 开放决策（A 必须拍板才能转正式 PRD）

以下 7 个决策在 M3 开工前必须定，否则会导致 spec/plan 分叉：

1. **M3 的"完成"定义**：只包含 P0？包含 P0+P1？全部？
2. **Operator 鉴权的 session 存储**：SQLite 还是加 Redis？
3. **RBAC 粒度**：先做粗粒度（viewer/responder/admin 三级）还是细粒度（基于 permission matrix）？
4. **Subtenant URL 路径约定**：`/t/<b>/t/<c>/` 还是 `/s/<c>/`？
5. **Subtenant 是否归属 B 的计费**：计费归 B（B 的发票列 C 用量）还是平台直接计费给 C？
6. **Triage 增强优先级**：Handoff 和 SLA 哪个先做？（建议 SLA 先——直接兑现 M2 承诺；Handoff 依赖 agent 成熟度）
7. **E2E Playwright 是否必须 M3 进**：17 story 自动化工作量不小（旧 M5 Batch 14 规划了 2 天）——可推 M4

## 7. 不属于本 PRD 的 M3 候选项

以下是 M2+triage 两处 Out-of-scope 清单之外、但可能被考虑进 M3 的候选项（需 A 决定是否纳入）：

- 多语言 UI 扩展（当前只 zh/en；新增 ja/es/...）
- 知识库版本管理（tenant 改 soul 时回滚能力）

- 服务端压测 + 性能基线
- 跨 region 部署架构（目前隐式 single-region）

这些我没列进上面的 Epic 是因为**没有明确业务信号**。如果 A 有其中某项的需求，告诉我，我补到对应 Epic 下。
