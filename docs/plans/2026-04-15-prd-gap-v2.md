## 一、P0 冲突 Spike 结论

### 1.1 占位续写可行性 × 飞书限频

**冲突重述**:
- PRD US-2.2 承诺：1s 占位 + 5–15s 续写，客户感知"一条完整回答"
- PRD SLA §6：占位消息 <1s · 慢查询续写 <15s · 平均首回 <60s
- 飞书 API 限制：`PATCH /im/v1/messages/:id` 单条消息 **5 QPS**、**14 天有效期**；PUT 仅 text/post；卡片需 `update_multi:true`

**Spike 分析（基于官方文档 + 已有 channel_server 实现）**:

| 场景 | QPS 估算 | 是否超限 | 结论 |
|---|---|---|---|
| 单对话占位续写（1 次 PATCH） | 0.07 QPS (15s 内 1 次) | ✅ | 主线路径可行 |
| 单对话流式续写（每 500ms 刷新） | 2 QPS | ✅ (单消息 5 QPS) | 流式可行 |
| 单对话流式续写（每 200ms 刷新） | 5 QPS | ⚠️ 边界 | **必须 ≥250ms 间隔** |
| 分队群 10 活跃对话同时刷新摘要 | 单群 5 QPS | ❌ **超限** | 需聚合 |

**决策（替代 T0.3）**:
1. **主方案保持卡片 PATCH**，但续写阶段限频为 **最快 250ms/次，默认 500ms/次**；单卡实际 PATCH 次数上限 29 次（留安全余量于 50 次上限）
2. **分队群摘要刷新必须走聚合器**：同一群内所有 active 对话卡片的 PATCH 由 `CardRefreshCoalescer` 统一排队，全局 ≤4 QPS（预留 1 QPS 给其他消息）；摘要变化不足 token-diff 阈值时跳过
3. **14 天有效期超期处理**：对话超过 12 天仍活跃时，自动 close 老卡片 + 发新卡片；`Conversation` 表新增 `card_id, card_sent_at` 字段
4. **降级路径**：若续写超 15s 仍无结果，PATCH 从"加载中"改为"请稍候，复杂问题已升级至深度查询"；超 30s 触发 Agent @人工 自动求助
5. **SLA 不变**：PRD 承诺在这个限频下仍可达成，无需调整 PRD

**新增任务**:
- **T0.3' 重新定义**: 只做 **客户端视觉验证**（闪烁/通知/滚动），技术可行性已由此 spike 关闭
- **新增 T1.10a**: 实现 `CardRefreshCoalescer`（500ms 滑窗 + diff 判断 + 群级排队）
- **新增 T1.10b**: 实现卡片 14 天换卡机制（`CardLifecycleManager`）

### 1.2 飞书权限审批 × ≤2h 自助上线

**冲突重述**:
- PRD US-1.2：勾 4 权限 → 5 秒建群 + 4 Agent 入群
- PRD US-1.4：整个上线向导 **≤ 2 小时**
- Feishu API 验证 §四：新增权限 `im:message:update` / `im:chat:create` / `approval:approval` 等需飞书开放平台审批（周期不可控，通常 1–5 工作日）

**Spike 分析**:

审批周期属于 **AutoService 应用级别**（一次性，对商户透明），而非 **商户上线时** 要审批。两者关系如下：

```
[AutoService 应用] ── 向飞书申请权限 ── [飞书审批 1-5 天，一次性]
        │
        └──(已授权 scope)──> [商户老陈安装应用] ── 勾选权限 → 建群 ──[秒级]
```

商户勾选的是 **已由 AutoService 预审过** 的 scope 子集；商户侧无需再走飞书审批。

**决策**:
1. **P0 必做（商务前置）**: 在 Phase 0 完成时 **必须** 已向飞书商店提交所有 P0-P2 权限审批。此工作应由项目经理在第 1 周 Day 1 启动（T1.8 提前至 T0.0）
2. **权限分级发布策略**: 
   - **MVP v1**（内测商户用）：开发者后台自建应用，跳过应用商店审批，仅限白名单租户
   - **MVP v2**（对外开放）：上架飞书应用商店，需完整合规审批（2–4 周）
3. **PRD US-1.2 "5 秒建群" 承诺仍成立**，因为：
   - AutoService 应用已预审 `im:chat:create` + `im:chat.members:write_only`
   - 商户安装时只需 OAuth 同意，不走二次审批
4. **风险兜底**: 若个别敏感权限（如 `contact:user.employee:readonly`）审批驳回，降级方案：用 open_id 替代 user_id，所有设计已基于 open_id（见 API 验证 §2.4.2 "商店应用不能用 user_id"）

**新增任务**:
- **T0.0（新，周 0 Day 1）**: 提交飞书开放平台审批，权限清单见 feishu-api-verification §四
- **T0.0a**: 同步提交 Lark 国际版审批（独立流程）
- **T1.8 改为**: "验证所有权限已生效"（从申请改为验证）

### 2.2 虚拟客户预演自动生成 + 审阅 UI（US-1.3 / E1.3）

**对 T?.? 的细化**（v1 标"部分实现/8 UAT 用例"，缺自动生成 prompt 和审阅 UI）。

**自动生成 prompt 方案**:

输入：
- 商户上传的产品目录/FAQ（RAG 检索源）
- 目标客户地区/语言配置
- 历史对话 CSV（若有）

生成流程（`autoservice/sim_customer.py`）:

```python
# Pseudocode
def generate_sim_dialogs(tenant_id, n=12) -> list[SimDialog]:
    scenarios = classify_business_scenarios(kb)  # 从 KB 聚类出 5-8 个主题
    personas = ["angry-refund", "price-sensitive", "non-native-speaker",
                "tech-illiterate", "repeat-customer", "cross-border"]
    dialogs = []
    for scenario in scenarios:
        for persona in sample(personas, 2):
            dialog = slow_llm.generate(
                system=SIM_CUSTOMER_PROMPT,
                scenario=scenario, persona=persona,
                constraints={"turns": (3, 6), "must_include": scenario.keywords}
            )
            ai_response = production_agent.reply(dialog.last_turn)
            dialogs.append(SimDialog(scenario, persona, dialog, ai_response))
    return dialogs  # ≥10 条，覆盖主要场景
```

`SIM_CUSTOMER_PROMPT` 要求：
- 产出真实客户用语（含口语、错别字、不完整描述）
- 每场景至少一个"陷阱"（问不在 KB 内的边缘问题）
- 语言与商户目标地区匹配

**审阅 UI**（基于 Web 管理后台）:

```

│ [场景: 退款申请 · 客户型: angry-refund]    │
├──────────────────────────────────────────┤

│  > 我昨天下的单要退，钱多久到？            │
```

### 2.3 SLA 埋点清单 + 滚动聚合算法（US-3.1/3.3 / E3.3）

**对 T3.14 / T3.15 的细化**（v1 仅写"5 分钟滚动窗口检测"，缺埋点事件和算法）。

**埋点事件清单**:

| 事件 | 触发点 | payload | 对应 SLA |
|---|---|---|---|
| `chat.opened` | 客户点开浮窗 | `{conversation_id, ts}` | 首屏应答 <3s |
| `greeting.sent` | Agent 首条消息发出 | `{conversation_id, ts}` | 首屏应答 <3s |

| `answer.completed` | 续写完成或直接回答 | `{conversation_id, ts, query_id, model_used}` | 续写 <15s |
| `escalation.requested` | Agent @人工 发出 | `{conversation_id, ts, reason}` | 接单等待 <180s |
| `human.first_reply` | 人工第一条消息 | `{conversation_id, ts, agent_open_id}` | 首回 <60s |
| `human.takeover.started` | 进入 HumanTakeover | `{conversation_id, ts}` | 接管次数 ★ |
| `conversation.closed` | 对话结案 | `{conversation_id, ts, csat, resolution}` | CSAT ★ · 会话时长 |

| `proposal.accepted` | Agent 采纳人工建议 | `{conversation_id, proposal_id}` | 提议采纳率 |

**SLA 派生指标（5 分钟滚动窗口）**:

```python
# autoservice/metrics.py
class SLAAggregator:
    WINDOWS = {"5m": 300, "1h": 3600, "24h": 86400}

    def rolling(self, metric, window="5m", tenant_id=None):
        # 时间序列 DB (内存环形 buffer + 周期 flush 到 Bitable)
        ...

    def first_response_p50(self, window="5m"):
        pairs = self.join("chat.opened", "greeting.sent", window)
        deltas = [b.ts - a.ts for a, b in pairs]
        return percentile(deltas, 50)

    def human_queue_time_p95(self, window="5m"):
        pairs = self.join("escalation.requested", "human.first_reply", window)
        deltas = [b.ts - a.ts for a, b in pairs]
        return percentile(deltas, 95)

    def check_alerts(self, tenant_id):
        if self.human_queue_time_p95() > 180:
            emit("sla.breached", {metric: "queue", value, threshold: 180})
```

**告警规则**:

| 指标 | 阈值 | 窗口 | 动作 |
|---|---|---|---|
| 首回 P95 | >60s | 5m | 管理群告警卡片 |
| 接单等待 P95 | >180s | 5m | 管理群告警卡片 + /dispatch 按钮 |
| CSAT 均值 | <4.0 | 1h | 管理群通知 |
| AI 消化率 | <70% | 24h | 管理群建议"可能需要 Dream Engine 补训" |

## 三、粒度不足项深化（4 项）

### 3.1 六步状态机与 SLA 约束映射（C1 / T1.1~T1.4）

**v1 仅"6 状态 + 转换规则"，缺每步 SLA 和超时行为**。

**状态机完整定义**:

| 状态 | 对应 PRD 步 | 入场条件 | SLA 约束 | 超时动作 | 可发事件 |
|---|---|---|---|---|---|
| `CustomerTriggered` | ①顾客触发 | 首条消息到达 | 3s 内进入下一态 | 超时：SRE 告警（系统卡死） | `chat.opened` |
| `AgentHandling` | ②Agent 接洽 | 分流 Agent 路由完成 | 首回 <3s（US-2.1）/ 占位 <1s（US-2.2） | 超 15s 无续写 → PATCH 卡片为"升级中" | `greeting.sent`, `placeholder.sent`, `answer.completed` |
| `CopilotSupervising` | ③对话监管 | 人工点开分队卡片 | 无硬 SLA（被动） | — | `copilot.opened`, `proposal.submitted` |
| `HumanAlerting` | ④人工提醒 | Agent @人工 或 `/hijack` | 接单等待 <180s | 180s 未接 → 退回 `AgentHandling` + 安抚消息 | `escalation.requested`, `escalation.timeout` |

### 3.2 ModelRouter 快慢决策树 + timeout 策略（B7 / T2.6~T2.7）

**v1 仅"根据复杂度选池"，缺决策树**。

**决策树**:

```
客户消息到达
    │
    ▼
┌─────────────────────────────────────┐
│ Fast Classifier (haiku, <200ms)    │
│ 分类为以下类别之一:                  │
│  · greeting            → fast-only  │
│  · simple-faq-hit (KB 命中率>0.9)  → fast-only
│  · complex-query (需多跳/长推理)   → fast-placeholder + slow-answer
│  · transactional (涉及 CRM/订单)   → slow-only + placeholder
│  · out-of-scope                    → escalation
└─────────────────────────────────────┘
    │
    ├─ fast-only: haiku 直答，不发占位
    ├─ fast-placeholder + slow-answer:
    │    1. haiku 立即生成占位（"稍等，正在为您查询..."+ 预估时间 ≤1s）
    │    2. 发卡片（update_multi:true）
    │    3. sonnet 并行跑（5-15s timeout）
    │    4. 完成 → PATCH 卡片续写
    │    5. timeout → PATCH "复杂问题已升级至深度查询，客服同事正在介入"
    │                + 触发 escalation
    └─ slow-only: 同上但快模型只发占位不生成内容
```

**Timeout 策略**:

| 阶段 | 目标 | 硬超时 | 超时动作 |
|---|---|---|---|
| Fast Classifier | 200ms | 500ms | 默认走 slow-only 路径 |
| Fast Placeholder | 1s | 2s | 若超时，占位退化为静态字符串"正在查询..." |
| Slow Answer | 10s | 15s | PATCH 升级文案 + 自动 escalation |
| Slow Answer extended | 25s | 30s | 强制 `HumanAlerting` 状态 |

**快慢协同协议**:
- 慢模型 streaming 时每 500ms 汇总 → CardRefreshCoalescer → PATCH 卡片
- 慢模型 token count 超过 2k 时，提前 PATCH 一次"已整理 X 要点，继续补充中..."
- 快慢两侧通过 `query_id` 关联；Conversation 表新增 `pending_queries[]`

**新增任务**:
- **T2.6 细化**: `autoservice/model_router.py` 含 FastClassifier（haiku 分类 prompt）
- **T2.6a（新）**: `classify_intent.yaml` 分类 schema
- **T2.7 细化**: 4 阶段 timeout 行为 + 降级文案模板

### 3.3 Agent 分队频道 + 卡片 + 侧栏 Copilot 交互细节（C3~C5 / T3.1~T3.9）

**v1 仅列 API 和方法签名，缺交互时序和 UI 状态**。

**分队频道卡片状态**（对话摘要卡）:

| 卡片状态 | 触发 | 卡片标题 | 按钮 |
|---|---|---|---|
| `idle` | Agent 接洽中 | "🟢 对话 #42 · 客户 David" | [点开监管] |
| `waiting-reply` | 等客户回复 | "⌛ 对话 #42 · 等客户" | [点开监管] |
| `escalation-pending` | Agent @人工 | "🔔 对话 #42 · 需接单 (120s)" | [立即接管] [转他人] |
| `human-takeover` | 人工 driver | "👤 对话 #42 · 小李接管中" | [查看 thread] |
| `closed` | 结案 | "✅ 对话 #42 · 已结案 · CSAT 5" | [复盘] |

卡片 body 固定 3 行摘要 + 最新情绪标签 + 未读数徽章。

**侧栏 Copilot（点开卡片后）**:

PRD US-2.4 要求"弹出聊天窗，默认 copilot 模式"。飞书客户端实现：

- 点卡片 → 跳转到对应 thread（独立话题）
- Thread 内看到：客户消息（淡蓝）+ Agent 拟回复草稿（黄框标记 `[草稿·未发送]`）
- 人工在 thread 输入 → 消息仅对 Agent/人工可见（不发客户），加标签 `[建议]`
- Agent 采纳 → 草稿更新 → 确认后走正常消息通道发给客户 + thread 内记录 `[已采纳·已发送]`

**角色翻转后（`AgentCopiloting`）**:
- 人工在 thread 的消息 → **直接发客户**（非建议模式）
- Agent 持续在 thread 发 `[AI 建议] xxx` → 对客户隐藏
- 客户端看到：顺畅的对话流，感知不到切换（US-2.6）

**thread 内消息路由规则**:

| 发送者角色 | 内容前缀/标签 | 客户端可见？ | 计入计费 |
|---|---|---|---|
| Agent（草稿态） | `[草稿]` | ❌ | — |
| Agent（已采纳） | 无 | ✅ | — |
| 人工（Copilot 态） | `[建议]` | ❌ | 提议次数++ |
| 人工（Takeover 态） | 无 | ✅ | 接管次数++ |
| Agent（Copilot 态下 AI 建议） | `[AI建议]` | ❌ | — |

**新增任务**:
- **T3.4 细化**: 5 种卡片状态 JSON 模板
- **T3.8 细化**: thread 内消息路由表实现
- **T3.9 细化**: 草稿态 / 已采纳态流转（events：`draft.pending`, `draft.adopted`）

### 3.4 灰度升阶与回滚决策引擎（D6~D7 / T5.2~T5.3）

**v1 仅"24h 无下跌自动升阶"，缺阈值**。

**升阶决策**（每个阶段运行 24h 后判断）:

| 指标 | 基线 | 允许波动 | 升阶判定 |
|---|---|---|---|
| CSAT 均值 | 上阶段数值 | ≥ 基线 − 0.2 | 必须满足 |
| 升级转结案率 | 上阶段数值 | ≥ 基线 − 3% | 必须满足 |
| AI 消化率 | 上阶段数值 | ≥ 基线 − 5% | 必须满足 |
| 人工接单等待 P95 | 上阶段数值 | ≤ 基线 + 30s | 必须满足 |
| 投诉率 | 0 | 无新增投诉 | 必须满足 |

- 5 项全部满足 → 自动升阶（5% → 25% → 100%）
- 任一项不满足 → 停留当前阶段 + 管理群提示"监控中，今日不升阶"
- 任一项恶化超过 2× 阈值 → **自动回滚**（无需 `/rollback`）+ 管理群告警

**手动回滚路径**（`/rollback <proposal_id>`）:
1. 立即将该提案从所有 canary 流量中摘除
2. Agent 切回上一版 prompt / KB
3. 回写管理群 + 写入 `proposal.history` 表 `status=rolled-back, reason=<manager-note>`
4. 进入"待复盘"队列（7 天内复盘会议）

**新增任务**:
- **T5.2 细化**: `CanaryRouter` 含 5 指标监测 + 自动升阶/回滚
- **T5.2a（新）**: `alerts.yaml` 追加"灰度恶化"规则
- **T5.3 细化**: `/rollback` 必须伴随 reason 字段（避免滥用）
