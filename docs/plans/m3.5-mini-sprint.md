## 2. M3-landed backend pieces (dream-ui-augmentation carve-out)

Split from the dream-ui-augmentation plan and shipped before M3 gate (batch-10.5):

### T4S.3b · `GET /api/dream/status`
- Exposes `dream_scheduler.should_trigger()` `(bool, reason_code)` output
- Response: `{tenant_id, running, reason_code, last_run_summary?, next_eligible_at?}`
- Admin auth via `require_tenant_access` (rbac: `view_sla_dashboard`)
- ~20 LoC backend + ~5-8 tests

### T3S.7-hotfix · `/api/management/chat` blocks schema + fix 2 failing tests
- Extend response schema with optional `blocks?: Block[]` field
- Route dialog commands (`/dream-config`, `/rules`, `/status`, `/approve`, etc.) to existing dialog handler
- Unify response shape: `{role, content, reply?, blocks?}`
- Fix `tests/dream_scheduler/test_refresh.py::test_dream_config_confirm_calls_refresh` + `test_dream_config_cancel_does_not_call_refresh` (currently 422)

These two ship in M3 under batch-10.5 and are **not** part of M3.5.

- **Playwright flakiness** — budget 2-3h per Epic suite for timing/race debug

- **D2 (canary + Apply) UX complexity** — combines 4 backend APIs; likely needs visual design iteration
- **im-block schema creep** — P2 wants 3 block types; resist adding more in M3.5
